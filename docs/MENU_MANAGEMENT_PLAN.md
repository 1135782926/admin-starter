## 1. 目标与范围

采用独立菜单表关联现有 Spatie 权限体系。通过同一个菜单管理入口维护目录、菜单项和按钮权限，创建站内页面时批量生成基础权限。

本次包含：

- 菜单管理树、节点详情、创建、修改、删除和删除影响预览。
- 页面访问权限、按钮操作权限及对应鉴权规则。
- 供角色授权页面使用的权限选择树。
- 当前管理员可访问的前端路由树与按钮权限下发。
- 前端切换后端权限模式，调整环境模板、API 地址和菜单请求地址。
- 管理员登录、获取当前管理员信息和退出当前登录，以及对应前端接入。
- 默认数据库种子创建启用的 `admin` 超级管理员，初始密码为 `admin`；重复执行不覆盖已修改的密码。

本次不包含：

- 角色 CRUD 和角色授权保存接口。
- 菜单管理页面开发（初始批次范围，已在后续轮次实现）。
- 公开注册、找回／修改密码、角色分配接口和设备会话管理页面。
- 截图中的“只作为路由／只作为菜单”等特殊扩展属性。
- 权限变更实时推送。

管理员认证现已纳入实施范围，应先接通登录、用户信息和 Token 生命周期，再联调菜单。角色授权保存接口后续接入时，必须在服务端落实本文的授权联动规则。

## 3. 数据模型

### 3.1 菜单表

新增 `admin_menus`，建议模型为 `AdminMenu`。以下是实施字段约定：

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `id` | bigint 主键 | 菜单节点 ID |
| `parent_id` | nullable bigint | 上级菜单节点；根节点为 `null` |
| `type` | string | `directory`、`menu`、`button` |
| `title` | string | 显示名称 |
| `name` | string，唯一 | 全局唯一节点标识，创建后固定 |
| `permission_id` | nullable bigint，唯一 | 关联 `admin_permissions.id`；目录为空，菜单项和按钮必须绑定 |
| `open_type` | nullable string | 菜单项使用 `page`、`external`、`iframe` |
| `path` | nullable string | 前端路由路径；目录、菜单项使用 |
| `component` | nullable string | 站内页面组件路径 |
| `url` | nullable string | 外链或 Iframe 地址 |
| `icon` | nullable string | 图标 |
| `sort` | integer | 默认 `0`，升序排列，同值按 `id` 升序 |
| `keep_alive` | boolean | 默认 `false`，仅站内页面有效 |
| `status` | boolean | 默认 `true`，节点自身启用状态 |
| `remark` | nullable text | 备注 |
| `created_at`、`updated_at` | timestamps | 时间戳 |

约束：

- `parent_id` 关联本表；禁止通过数据库级联删除整棵子树。
- `permission_id` 关联现有权限表，避免绕过菜单维护流程直接删除仍被引用的权限。
- 对 `parent_id` 和排序查询建立必要索引。
- 节点标识和权限名称使用唯一约束，重复创建返回校验错误。
- 菜单项、按钮各绑定一个专属权限；不允许多个节点共享同一个权限。
- 不新增另一套角色授权关联表，继续使用 Spatie 现有表。

### 3.2 节点结构

| 节点类型 | 允许父级 | 允许子节点 | 是否绑定权限 |
| --- | --- | --- | --- |
| 目录 `directory` | 根节点、目录 | 目录、菜单项 | 否 |
| 菜单项 `menu` | 根节点、目录 | 按钮 | 是，页面访问权限 |
| 按钮 `button` | 菜单项 | 无 | 是，操作权限 |

- 目录和菜单项可以调整父级，但不能移动到自身或后代下。
- 节点类型创建后不可修改。
- 按钮不能跨菜单移动；应在目标菜单新建权限并重新授权。
- 调整目录、菜单父级不修改节点自身状态和已有权限 ID；有效状态按新祖先链计算。

## 4. 菜单与权限绑定

以商品管理为例：

| 节点 | `name` | 权限名称 | 用途 |
| --- | --- | --- | --- |
| 商品管理 | `goods` | `goods.access` | 显示菜单、进入页面 |
| 查看 | `goods.view` | `goods.view` | 查询列表、查看详情 |
| 添加 | `goods.create` | `goods.create` | 新增商品 |
| 编辑 | `goods.update` | `goods.update` | 修改商品 |
| 删除 | `goods.delete` | `goods.delete` | 删除商品 |

生成规则：

1. 创建站内页面时，始终生成该菜单的访问权限。
2. 默认额外生成查看、添加、编辑、删除四个按钮节点和操作权限。
3. 未传 `buttons` 时使用默认四项；传入空数组时不生成基础按钮；传入部分选项时仅生成所选按钮。
4. 默认创建会产生 5 个菜单节点、5 条权限记录。
5. 目录不生成权限；外链和 Iframe 仅生成自己的访问权限，不自动生成四项操作权限。
6. 后续可以新增导出、审核、上架等自定义按钮，例如 `goods.export`。
7. 默认四项仅在创建页面时批量生成，修改菜单不会补建已删除的按钮。
8. 节点和权限在同一事务中创建，任何一步失败均回滚。

节点标识和权限名称创建后固定。标题、图标、排序、路由、组件等修改不会改变权限标识和原有授权。

**菜单配置不注册后端路由。** 后端业务 API 在代码中明确声明所需权限；前端路由路径、组件路径与后端 API 地址分别维护。

## 5. 授权与鉴权

### 5.1 普通角色

- 角色授权以 `permission_id` 为准，不能将菜单节点 `id` 当作权限 ID 保存。
- 勾选操作权限时，自动补上所属菜单的访问权限。
- 单独勾选菜单访问权限，不自动授予任何操作权限。
- 取消菜单访问权限时，清除该角色在该菜单下的操作权限。
- 上级目录根据可访问后代自动展示，不单独授权。
- 新增按钮权限不自动授予已有角色；需要另外分配。
- 前端勾选联动只改善交互，角色授权保存接口也必须执行同样的服务端规则。
- 用户拥有多个角色时，按有效权限并集处理；已有直接授权也参与计算。

### 5.2 超级管理员

使用固定角色名称 `super-admin`：

- 自动拥有全部已启用菜单及操作权限，无须逐项分配。
- 仍受管理员账号状态、节点状态、祖先节点状态限制。
- 默认 `AdminUserSeeder` 创建 `admin / admin` 并分配该角色；重复执行不重置密码。初始口令仅用于本地初始化，部署后必须立即更换。

### 5.3 后端请求检查

管理员接口只允许有效、启用的 `AdminUser`，普通 `User` 即使 ID 相同也不能访问。

对绑定菜单权限的受控业务接口，检查：

1. 管理员身份与账号启用状态。
2. 目标节点及所有祖先节点均启用。
3. 普通管理员拥有所属菜单的访问权限。
4. 普通管理员拥有当前操作权限；超级管理员跳过授权分配检查。

Spatie 原有授权结果本身不包含菜单启用状态和祖先状态。实现时统一封装这部分鉴权入口，所有受控接口必须经过该入口，避免只调用原始 `can()` 而漏掉分支禁用检查。超级管理员的放行也不能绕过状态检查。

此处的“受控接口”指在代码中明确绑定权限检查的 API。创建菜单或按钮不会自动让任意业务 API 具备鉴权。

### 5.4 生效时间

- 权限、角色或节点状态变更后，后续请求使用最新结果。
- 涉及 Spatie 缓存的变更应正确清理权限缓存，注意事务提交与缓存失效的顺序。
- 首版不增加菜单树的跨请求缓存，避免额外的失效链路。
- 已打开页面的按钮可能暂时显示旧状态，后端仍按最新权限处理；刷新菜单或重新登录后更新前端显示。

## 6. 修改、禁用和删除

### 6.1 禁用

- 禁用目录：整个后代分支不可用，对应受控接口禁止访问。
- 禁用菜单：该页面及其按钮操作均不可用。
- 禁用按钮：只禁止该操作。
- 不清除已有授权，不批量改写后代的 `status`。
- 重新启用后按原有授权恢复；原本单独禁用的后代仍保持禁用。

### 6.2 删除

- 有子节点时拒绝删除，必须先处理子节点。
- 删除叶节点前，展示受影响的角色数和直接授权用户数，并要求管理者确认。
- 删除叶节点时，同一事务内清理菜单节点、专属权限、角色权限关联和用户直接授权关联。
- 目录没有专属权限，只在无子节点时删除目录自身。
- 删除预览仅供确认；实际删除时重新检查子节点及当前关联，不能依赖旧预览结果。
- 重建同名节点属于新权限记录，不恢复已删除的授权。

## 7. API 契约

统一前缀建议为 `/api/v1/admin`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/menus` | 管理端完整菜单树，包含按钮和禁用节点 |
| GET | `/menus/permission-tree` | 供角色授权使用的权限树 |
| GET | `/menus/{menu}` | 节点详情 |
| POST | `/menus` | 创建节点，站内页面支持批量创建基础按钮 |
| PATCH | `/menus/{menu}` | 修改标题、配置、父级、排序和状态 |
| GET | `/menus/{menu}/deletion-impact` | 删除影响预览 |
| DELETE | `/menus/{menu}` | 管理者确认后删除叶节点 |
| GET | `/me/menus` | 当前管理员的路由树及按钮权限 |

### 7.1 接口授权

菜单管理自身使用以下权限：

| 接口操作 | 所需操作权限 |
| --- | --- |
| 管理树、节点详情、删除影响预览、权限选择树 | `system.menu.view` |
| 创建 | `system.menu.create` |
| 修改 | `system.menu.update` |
| 删除 | `system.menu.delete` |

普通管理员还需拥有 `system.menu.access`。首版权限选择树沿用菜单管理查看权限；后续角色管理模块如果需要独立开放该接口，应显式增加对应角色管理鉴权规则。

`/me/menus` 只要求有效、启用的管理员身份，返回本人可访问的内容，不要求拥有菜单管理权限。

### 7.2 创建站内页面示例

```json
{
  "parent_id": 1,
  "type": "menu",
  "title": "商品管理",
  "name": "goods",
  "open_type": "page",
  "path": "/goods",
  "component": "/goods/index",
  "icon": "ri:shopping-bag-line",
  "sort": 10,
  "keep_alive": false,
  "status": true,
  "buttons": ["view", "create", "update", "delete"]
}
```

`parent_id: 1` 仅为示例，实际必须指向存在且类型允许的父节点。

### 7.3 按类型校验

- 目录：要求标题、唯一节点标识和前端路由路径，不接受权限、按钮操作或页面打开配置。
- 站内页面：要求路由路径和组件路径，不接受外链地址。
- 外链和 Iframe：要求路由标识所需的路径及有效的 HTTP／HTTPS URL，不接受站内组件和页面缓存配置。
- 按钮：要求菜单项父级、标题和唯一权限标识，不接受路由、图标、组件和页面缓存配置。
- 自动生成的权限名称由后端计算，不接受客户端任意绑定已有 `permission_id`。
- `type`、`name`、专属权限名称创建后禁止变更。
- `buttons` 仅用于创建站内页面；修改菜单时不使用该字段重新生成权限。
- 管理树不分页；节点同级按 `sort`、`id` 升序排列。

### 7.4 返回结构和状态码

前端现有 `BaseResponse<T>` 和请求拦截器要求成功响应使用：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": []
}
```

前端封装会取出 `data` 返回给调用者。实现 Resource 时必须与这一外层结构适配，避免额外产生 `data.data`。

- 查询、修改、删除成功使用 HTTP 200；创建可使用 HTTP 201，但成功响应体的 `code` 保持 200，以兼容现有拦截器。
- 删除成功可返回 `data: null`，不直接返回空的 HTTP 204。
- 未认证、账号禁用或 Token 失效返回 HTTP 401；菜单／按钮禁用或无业务权限返回 HTTP 403；节点不存在返回 HTTP 404。
- 字段校验失败返回 HTTP 422，并保留字段级错误信息。
- 有子节点禁止删除等结构冲突使用 HTTP 409。
- 错误响应使用真实 HTTP 状态码，并按现有前端错误处理适配消息字段，不以 HTTP 200 伪装失败。

## 8. 两种树的输出

### 8.1 管理树与权限选择树

管理树保留完整节点信息，按钮作为子节点，禁用节点也返回。

权限选择树至少包含：

- 菜单节点 `id`、`parent_id`、`type`、`title`。
- `permission_id` 和完整权限名称。
- 节点自身状态与综合祖先计算的有效状态。
- 访问权限与操作权限的依赖关系。
- 目录为分组节点，没有可保存的权限 ID。

不要把菜单 ID 和权限 ID 混成同一个树节点值后直接保存授权。

### 8.2 当前管理员路由树

沿用现有 `AppRouteRecord`：`name`、`path`、`component`、`meta`、`children`。

- 过滤禁用分支、无访问权限页面和无可访问后代的目录。
- 按钮不注册为 Vue Router 路由，放入所属页面的 `meta.authList`。
- `meta.authList` 仅返回当前管理员有效拥有的操作权限。
- 标题、图标、缓存分别映射为 `meta.title`、`meta.icon`、`meta.keepAlive`。
- 外链和 Iframe 分别使用现有 `meta.link`、`meta.isIframe` 约定。
- 目录使用现有布局处理方式，不把后端的 `directory` 字符串直接作为组件路径。

基础按钮标识映射：

| 后端完整权限 | 前端 `authMark` |
| --- | --- |
| `goods.view` | `view` |
| `goods.create` | `add` |
| `goods.update` | `edit` |
| `goods.delete` | `delete` |
| `goods.export` | `export` |

前端使用局部操作标识适配现有 `hasAuth('add')`、`hasAuth('edit')`；后端始终检查完整权限名称。自定义按钮从所属菜单的权限前缀下提取操作标识，不能只取任意权限名的最后一段而丢失上下文。

## 9. 前端接入

### 9.1 环境配置

本地 `web/.env` 和提交到仓库的 `web/.env.example` 均改为：

## 12. 管理员认证接口

### 12.1 单令牌方案

使用一个 Sanctum Token 完成管理员认证，不增加另一套刷新凭据。这个 Token 直接用于业务接口，语义上属于访问令牌，字段名保持前端现有的 `token`。

- 管理员仅从 `admin_users` 认证，不查询普通 `users`，不使用前端选择的角色作为授权依据。
- Token 默认自签发起有效 7 天，使用期间不自动延长期限；到期后重新输入账号密码登录。
- 有效期由后端配置，前端不能指定；每次接口请求都校验 Token 与管理员状态。
- 允许多个终端独立登录；再次登录不踢出其他终端，退出只撤销当前 Token。
- 不新增登录会话表，直接使用现有 Sanctum `personal_access_tokens`。
- 不实现刷新接口、双令牌轮换、自动续期或请求重放。
- 不新增注册、密码找回、修改密码、踢出全部终端或设备列表等接口。

请求与用户信息字段继续沿用现有前端定义；登录响应调整为只有 `token`，前端同步删除原来未实际使用的 `refreshToken` 字段和状态。

官方对自有 SPA 推荐 Cookie／Session 认证。本方案沿用现有前端的 Token 登录与持久化流程，明确使用 Bearer Token，不同时维护 Cookie 登录流程。锁文件中 `laravel/sanctum` 为 `v4.4.0`，编码时确认实际安装版本；API 行为参考 [Sanctum 官方文档](https://laravel.com/docs/13.x/sanctum#api-token-authentication)。

### 12.2 接口清单

下列路径均带 `/api/v1/admin` 前缀：

| 方法 | 路径 | 凭据 | 用途 |
| --- | --- | --- | --- |
| POST | `/auth/login` | `userName`、`password` | 账号密码登录，签发 Token |
| GET | `/me` | `Authorization: Bearer <token>` | 获取当前管理员信息 |
| POST | `/auth/logout` | `Authorization: Bearer <token>` | 撤销当前 Token，无请求体 |

除登录外，上述接口及全部菜单接口要求有效的管理员 Bearer Token。普通用户 Token、仅有浏览器 `web` Session 的身份不能用于这些管理员接口；必须验证 Token 所属模型为 `AdminUser`，不能只比较用户 ID。

### 12.3 登录请求

```json
{
  "userName": "administrator",
  "password": "example-password"
}
```

| 字段 | 规则 | 映射 |
| --- | --- | --- |
| `userName` | 必填字符串，最长 255；去掉首尾空白后按现有用户名唯一性规则匹配 | `admin_users.username` |
| `password` | 必填字符串；登录不复用注册时的密码复杂度限制，不裁剪首尾空白 | 校验 `admin_users.password` 的哈希 |

不要对密码使用默认字符串裁剪；对这一请求字段配置必要的中间件例外。用户名不要擅自转小写，必须与现有用户名创建、查询和数据库唯一约束保持一致。

登录流程：

1. 校验字段，按管理员用户名查询。
2. 使用 Laravel 密码哈希校验；不自行计算明文密码摘要，不直接比较密码字段。
3. 账号不存在、密码错误、账号禁用统一返回 HTTP 401，消息为“账号或密码错误，或账号不可用”，不透露账号是否存在。
4. 无效账号查询也执行等价密码哈希校验，避免明显的时间差；日志不记录密码或 Token 明文。
5. 对有效账号按框架哈希配置处理必要的密码重新哈希。
6. 使用 Sanctum 签发带到期时间的 Token，成功后只在响应中返回一次明文。

登录按“规范化用户名 + IP”限速，默认每分钟 5 次，并增加按 IP 每分钟 60 次的上限。超过限制返回 HTTP 429 和可用的重试提示。

### 12.4 登录响应与 Token 使用

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "token": "<Sanctum Token 明文>"
  }
}
```

尖括号内容表示接口契约中的令牌值，实施时必须由后端实际签发，不硬编码示例内容。`token` 是不带 `Bearer ` 前缀的原始值。

前端将它存入现有 `accessToken`，调用受保护接口时发送：

```text
Authorization: Bearer <token>
```

- Token 使用现有 `personal_access_tokens` 的哈希存储，不新增凭据存储表。
- 使用 Token 自身的 `expires_at` 设置 7 天期限；`config/sanctum.php` 当前全局 `expiration` 为 `null`，如果后续调整全局期限，注意它可能提前截断本模块 Token 的有效期。
- 不向响应暴露 Token 摘要、数据库令牌记录、`remember_token` 或管理员密码字段。
- Token abilities 不保存会过时的角色和菜单权限快照；业务权限按实时角色及菜单状态判断。
- Token 过期或被撤销后返回 HTTP 401，前端清理本地登录态并跳转登录页，不自动换 Token 或重放请求。
- Token 被他人获取后，在到期或撤销前可被用于请求接口；单令牌简化方案接受这一凭据有效窗口。

### 12.5 当前管理员信息

`GET /api/v1/admin/me` 返回现有 `Api.Auth.UserInfo` 结构：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "userId": 1,
    "userName": "administrator",
    "email": "admin@example.com",
    "avatar": "/uploads/avatars/admin.png",
    "roles": ["super-admin"],
    "buttons": ["goods.view", "goods.create", "goods.update", "goods.delete"]
  }
}
```

示例表示该管理员在示例权限数据下的返回，不代表内置账号或自动授权。

| 前端字段 | 数据来源与规则 |
| --- | --- |
| `userId` | `admin_users.id`，数字类型 |
| `userName` | `admin_users.username`，不替换为昵称 |
| `email` | `admin_users.email`；数据库为空时返回空字符串，保持前端 `string` 类型 |
| `avatar` | 数据库有值时返回可访问的地址；无值时省略该可选字段，不伪造头像记录 |
| `roles` | 真实 Spatie 角色名称数组，例如 `super-admin`，不硬编码成模板的 `R_SUPER` |
| `buttons` | 按菜单及祖先状态过滤后的有效完整操作权限名称数组，包含角色与直接授权的并集，不包含目录或页面访问权限 |

`super-admin` 的 `buttons` 从当前有效的操作节点计算，不返回 `*`，也不从签发 Token 时的权限快照读取。

后端模式中的页面按钮展示仍以当前路由 `meta.authList` 为准；本接口的全局 `buttons` 不能替代页面上下文判断。前端保留的演示 `R_SUPER`／`R_ADMIN` 判断需要改成实际角色名。

如果管理员登录有效但没有任何菜单权限，`/me` 正常返回，`/me/menus` 返回空数组；前端显示“暂无可访问菜单”，不把它当成 Token 失效，也不退回演示菜单。

### 12.6 退出与账号禁用

- 退出使用当前 Bearer Token 认证，删除本次请求对应的 Sanctum Token，不删除管理员其他终端的 Token。
- 退出成功返回 HTTP 200、`code: 200`、`data: null`。
- Token 已过期或已撤销时，退出请求返回 HTTP 401，前端同样清理本地登录态，不需要先恢复认证再退出。
- 前端先发送服务端退出请求，再清理本地登录态；网络错误时也清理本地状态，但不能声称服务端凭据已成功撤销。
- 管理员禁用时撤销其全部 Token。每次受保护请求仍检查账号状态；重新启用后必须重新登录，不恢复旧 Token。
- 账号不可用使认证失效，返回 HTTP 401；菜单／按钮禁用或无业务权限返回 HTTP 403，不因此退出登录。

### 12.8 状态码与响应处理

| 情况 | HTTP 状态码 | 客户端处理 |
| --- | --- | --- |
| 登录、获取信息、退出成功 | 200 | 按 `code: 200` 取 `data` |
| 登录字段不合法 | 422 | 展示字段错误 |
| 登录凭据错误或账号不可用 | 401 | 展示统一登录失败提示 |
| Token 无效、过期、撤销或账号不可用 | 401 | 清理登录态，重新登录 |
| 账号有效但菜单／操作无权访问或被禁用 | 403 | 展示无权访问，保留有效登录态 |
| 触发登录限速 | 429 | 展示重试提示，不循环请求 |

成功和错误的外层 JSON 继续遵循第 7.4 节；登录响应带 `Cache-Control: no-store`，不把包含 Token 的响应缓存下来。
